# 智能康复臂带评委演示与答辩提纲

## 1. 演示目标

本次演示要让评委快速看到三件事：

1. 作品不是单一传感器显示，而是一个完整的上肢康复训练闭环系统。
2. 系统能从佩戴端采集动作数据，实时计算角度、次数、完成度、评分，并同步到 Web 端。
3. 作品面向脑卒中、术后恢复、上肢功能训练等康复场景，有实际使用价值和继续优化空间。

建议总演示时间控制在 5 到 8 分钟。

## 2. 一句话介绍

智能康复臂带是一套面向上肢康复训练的可穿戴评估系统，通过上臂端和手腕端的双 IMU 姿态采集，结合端侧特征计算、动作识别、训练评分、肌电状态估计和 Web 可视化分析，实现患者训练过程的实时反馈和康复数据留存。

更抓评委注意力的版本：

> 它解决的不是“能不能测到传感器数据”，而是康复训练里更实际的三个问题：动作有没有做到位，患者有没有主动发力，训练结果能不能被长期记录和分析。

现场可以先讲这句，再展开双 IMU、肌电 AI 和 Web 平台。

讲解重点：

可以这样说：

### 3.2.1 上臂端和手腕端界面说明

现场展示两个屏幕时，可以先讲“分工”，不要只说“这里有两个屏幕”。

上臂端界面可以这样介绍：

手腕端界面可以这样介绍：

> 手腕端是随身反馈界面。它不追求显示所有数据，而是显示患者训练时最需要快速看到的信息，包括蓝牙连接状态、电量、训练模式、健康监测、等待上臂端选择动作、训练中提示和断连提示。健康监测页面可以显示心率、血氧和脉搏趋势，训练页面主要提示用户跟随上臂端完成动作并保持正确姿势。

一句话总结：

> 上臂端负责“完整控制和完整数据”，手腕端负责“近身提示和健康入口”，Web 端负责“大屏展示和长期分析”。三个界面不是重复，而是面向患者、佩戴端和评委展示场景做了不同层级的信息分工。

讲解重点：

- 不是单动作演示，而是支持多类上肢训练。
- 不同动作读取不同角度特征。
- Web 端四个角度实时上传：肘关节、前臂旋转、手臂外展、肩部上举。

可以这样说：

> 系统目前支持四类上肢康复动作。每类动作对应的核心评估角度不同，比如肘关节屈伸主要看肘部弯曲角度，前臂旋转看旋转角度，手臂外展看外展角度，肩部上举看上举角度。训练过程中这些角度都会实时上传到 Web 端。

### 3.4 实时训练演示 2 分钟

建议主讲两个动作：前臂旋转和肘关节屈伸。

这样安排的好处：

2. 再切换到肘关节屈伸，缓慢完成 2 到 3 次，让评委看肘关节角度、次数、完成度和肌电状态。
3. 每次动作结束后展示结果页和历史记录。
4. 让评委看 Web 实时页面：
   - 当前动作
   - 当前角度
   - 完成度
   - 评分
   - 四个动作角度条
   - 设备状态

讲解重点：

- 角度实时变化。
- 次数达到目标后完成度增加。
- Web 和上臂端同步显示。
- 训练结果会进入历史记录。

前臂旋转可以这样说：

> 现在我先演示前臂旋转。这个动作主要体现双 IMU 的相对姿态计算，系统不是只看手腕端有没有转动，而是结合上臂端和手腕端姿态，计算前臂相对上臂的旋转角度。Web 端可以看到前臂旋转角度实时变化，动作完成后会形成训练记录。

肘关节屈伸可以这样说：

> 接下来演示肘关节屈伸。这个动作除了计算屈肘角度，还会结合肌电边缘 AI 模型判断肌肉参与状态。模型输出不是孤立使用，而是会根据当前屈肘角度和动作阶段进行框定，避免肌电瞬时波动造成不合理判断。这样能更接近康复训练中“动作幅度 + 主动发力”的综合评估。

### 3.5 肘关节屈伸加肌电边缘 AI 展示 1 分钟

如果现场肌电传感器稳定，可以演示；如果不稳定，就只作为功能说明。

讲解重点：

- 肘关节屈伸界面会展示肌电状态。
- 已使用边缘 AI 肌电模型进行 relax / weak / active 三分类。
- 模型输入不是原始 ADC，而是基线归一化后的肌电特征。
- 模型输出会结合屈肘角度、动作阶段和角度范围进行框定。
- 训练评价不仅看动作角度，也看患者是否有主动发力参与。

可以这样说：

> 在肘关节屈伸动作中，我们使用了部署在上臂端的边缘 AI 肌电模型。上臂端先通过 ADC 采集肌电信号，再提取静息基线、整流幅值、包络、RMS 等特征，模型根据这些特征判断放松、轻微发力和正常发力。为了让结果符合康复动作逻辑，我们不会直接把肌电模型输出当最终结论，而是再根据当前屈肘角度和动作阶段进行框定，例如角度很小或动作未进入有效屈肘区间时，不会显示成强发力训练状态。

注意：

- 可以说“已完成端侧模型训练、C 代码导出和 STM32 集成”。
- 不要说“医疗级诊断准确率”。
- 如果评委问准确率，可以说当前模型有训练报告和混淆矩阵，属于原型数据集验证；后续还需要更多受试者、多佩戴位置、多皮肤状态的数据做泛化验证。

## 4. 作品创新性怎么讲

### 4.1 双 IMU 相对姿态评估

创新点：

- 不是只看一个传感器的绝对角度。
- 通过上臂和手腕两个 IMU 的姿态差计算关节运动。
- 更适合上肢康复，因为康复关心的是关节活动范围，不是单个模块的空间姿态。

答辩说法：

> 我们使用双 IMU 是为了减少单点姿态判断的误差。比如患者身体整体移动时，单 IMU 可能误以为动作完成，但双 IMU 可以通过上臂和手腕之间的相对变化判断真正的关节活动。

### 4.2 训练闭环

创新点：

- 采集、识别、评分、反馈、记录、分析形成闭环。
- 不只是显示角度，而是把数据变成康复结果。

答辩说法：

> 我们的目标不是做一个传感器仪表，而是做康复训练闭环。患者做动作，系统实时反馈；训练结束后生成结果；长期数据进入历史记录，再用于康复分析和训练建议。

### 4.3 多模态融合

创新点：

- 姿态 IMU 用于动作角度。
- 肌电用于主动发力状态估计。
- 健康数据用于训练安全性辅助判断。
- Web 分析用于医生或康复师查看。

答辩说法：

> 康复评估不能只看一个指标。角度代表动作幅度，肌电代表主动发力参与，心率血氧等指标反映训练负荷。我们把这些信息汇总到同一个系统中，提高评估维度。

### 4.4 端侧实时处理

创新点：

- 主要计算在嵌入式端完成。
- Web 端负责展示和分析，不依赖云端才能运行。
- 更适合居家康复和弱网络环境。

答辩说法：

> 系统的基础训练判断在端侧完成，Web 端主要负责可视化和历史分析。这样即使网络不稳定，设备端仍然可以完成基本训练流程。

### 4.5 康复数据可追踪

创新点：

- 每次训练保存记录。
- 可查看历史趋势。
- 支持后续个性化训练建议。

答辩说法：

> 康复训练最重要的是长期趋势。一次动作做得好不代表恢复好，我们通过历史记录保存每次训练的次数、评分、角度和完成度，方便观察恢复过程。

## 5. 技术挑战怎么讲

### 5.0 可以主动强调的技术深度

如果评委更关注技术难度，可以主动补充下面这些点：

- 双 STM32U575 协同：上臂端和手腕端分别承担姿态采集、训练逻辑、显示交互、健康数据和无线通信任务。
- 双 IMU 相对姿态：不是单点角度显示，而是通过上臂端和手腕端姿态差推导康复动作角度。
- 多动作状态机：前臂旋转、肘关节屈伸、手臂外展、肩部上举分别有独立的角度特征、计数逻辑和评分逻辑。
- 边缘 AI 肌电模型：PC 端采集三类肌电数据，训练随机森林模型，再导出 C 模型集成到 STM32。
- 肌电角度框定：AI 输出还会结合屈肘角度和动作阶段做二次约束，避免肌电噪声导致误判。
- 手写 MQTT 报文：STM32 端没有直接依赖完整 MQTT 库，而是构造 MQTT CONNECT / PUBLISH 报文，通过 ESP8266 TCP 发送。
- HTTP + MQTT 双链路：HTTP 用于设备时间同步，MQTT 用于训练和健康数据实时上传。
- Web 实时推送：后端统一解析 HTTP / MQTT 数据，前端通过接口和实时事件更新训练界面。
- 本地历史记录：训练历史和健康历史保存到 JSON，Web 端读取后生成趋势和康复分析。
- RTC 时间闭环：设备从 Web 获取时间后写入 RTC，后续本地走时，降低频繁网络同步带来的阻塞风险。

答辩时不要一次全讲完。评委问技术难度时，优先讲“边缘 AI 肌电模型 + 双 IMU 姿态融合 + 手写 MQTT 链路”这三个点。

### 5.1 双端无线同步

挑战：

- 上臂端和手腕端采样时间不同。
- 无线链路会有延迟和丢包。
- 两端姿态要尽可能同步，否则关节角度会抖动。

答法：

> 我们通过周期性数据上传和状态包同步，尽量保证 Web 端接收到的是最新训练状态。对于时间显示，上臂端先通过 HTTP 从 Web 获取时间，然后写入 RTC，之后由 RTC 自己运行，减少频繁同步带来的阻塞。

### 5.2 姿态解算和角度稳定

挑战：

- IMU 有噪声和漂移。
- 动作过程中会有抖动。
- 不同佩戴位置会影响角度。

答法：

> 姿态计算需要做滤波和稳定判断。我们在动作评估中不仅看瞬时角度，还会结合峰值角度、平均角度、动作完成次数和稳定性，避免单次抖动直接影响结果。

### 5.3 多动作识别

挑战：

- 四种动作运动方向不同。
- 需要针对不同动作选取不同特征。
- 同一个动作可能因为佩戴者习惯不同产生差异。

答法：

> 我们没有用一个通用阈值判断所有动作，而是为不同动作建立不同的角度特征和计数逻辑。例如手臂外展关注外展角，肩部上举关注上举角，前臂旋转关注旋转角。

### 5.4 肌电信号不稳定

挑战：

- 肌电信号容易受皮肤接触、电极位置、噪声影响。
- 不同人的基线不同。
- 单次采样跳变明显。

答法：

> 肌电在原型阶段主要作为主动发力辅助指标。我们会先做基线、包络和 RMS 特征提取，再结合动作角度趋势进行平滑估计。后续如果有更多数据，可以做个体化校准和模型训练。

### 5.5 嵌入式资源受限

挑战：

- STM32 上计算、显示、通信、传感器读取要并行。
- 不能让 WiFi、HTTP 或屏幕刷新阻塞训练逻辑。
- 需要控制串口打印，避免影响实时性。

答法：

> 我们把实时训练、显示刷新、通信上传分开处理，并关闭不必要的调试打印。时间同步采用启动后获取时间并写入 RTC 的方式，避免频繁 HTTP 请求影响训练过程。

## 7. 关键知识点整理

### 7.1 IMU 是什么

IMU 是惯性测量单元，通常包含加速度计和陀螺仪，有些还包含磁力计。加速度计可以感知重力方向和加速度，陀螺仪可以感知角速度。通过融合算法可以估计设备姿态。

评委可能问：

> 为什么不用摄像头？

回答：

> 摄像头需要固定视角，容易受遮挡和光照影响，居家使用不方便。IMU 佩戴在身体上，可以随时采集动作，隐私性更好，也更适合可穿戴康复设备。

### 7.2 为什么要双 IMU

单 IMU 只能知道一个部位相对空间的姿态，双 IMU 可以计算上臂和手腕之间的相对变化，更适合判断关节运动。

评委可能问：

> 一个传感器不行吗？

回答：

> 可以做简单检测，但准确区分关节动作会比较困难。比如身体整体移动时，单传感器角度也会变化。双 IMU 可以通过相对姿态减少这种误判。

### 7.3 姿态解算

姿态解算是把加速度计和陀螺仪数据转换为角度或姿态的过程。常见方法有互补滤波、卡尔曼滤波、Madgwick AHRS 等。

答辩关键词：

- 加速度计长期稳定但动态时受干扰。
- 陀螺仪短期响应快但会漂移。
- 融合算法把两者优势结合起来。

### 7.4 关节角度计算

核心思路：

- 获取上臂端姿态。
- 获取手腕端姿态。
- 根据两个姿态的相对变化计算肘关节、旋转、外展、上举等角度。

不要说：

- “角度百分百等于医学测量角度。”

建议说：

> 这是面向康复训练反馈的相对角度估计，适合用于训练过程趋势和完成度判断。后续可以通过标准量角器或动作捕捉设备做标定，提高医学级精度。

### 7.5 动作计数

动作计数不是简单角度超过阈值就加一，而是要判断一个完整动作周期。

应包含：

- 起始状态
- 达到有效角度
- 返回或稳定
- 防止抖动重复计数

答辩说法：

> 我们会结合角度阈值、峰值、动作状态和防抖逻辑判断一次有效训练，避免角度在阈值附近抖动时重复计数。

### 7.6 训练评分

评分可以从多个维度组成：

- 完成度：完成次数和目标次数的比例。
- 幅度：最大角度是否达到训练要求。
- 稳定性：动作是否平稳。
- 发力状态：肌电是否反映主动参与。

答辩说法：

> 当前评分是面向演示和原型验证的综合评分，不直接替代医生诊断。它的价值在于给患者即时反馈，并为康复师提供训练趋势参考。

### 7.7 肌电 EMG

EMG 是肌肉电信号，能反映肌肉活动情况。

常见处理步骤：

1. 采样。
2. 基线估计。
3. 整流。
4. 包络或 RMS 特征提取。
5. 判断放松、轻度用力、明显用力。

评委可能问：

> 为什么肌电会跳变？

回答：

> 肌电是微弱生物电信号，受电极接触、皮肤阻抗、线缆干扰、佩戴位置影响很大，所以需要滤波、基线校准和个体化阈值。当前原型已经考虑用平滑和特征融合降低跳变影响。

### 7.8 RTC 时间同步

系统当前思路：

- 上臂端通过 HTTP 访问 Web 端 `/api/device-time` 获取当前时间。
- 写入 STM32 RTC。
- 后续由 RTC 自己走时。
- 周期性低频刷新，避免频繁 HTTP 阻塞。

评委可能问：

> 为什么不用一直从网络取时间？

回答：

> 频繁联网取时间会增加通信延迟和失败风险，也可能影响训练实时性。先同步一次再由 RTC 运行，更适合嵌入式设备。

### 7.9 Web 端作用

Web 端负责：

- 实时显示训练数据。
- 显示四个动作角度。
- 显示健康监测数据。
- 保存和读取训练历史。
- 生成康复分析和推荐动作。

评委可能问：

> 数据存在哪里？

回答：

> 当前原型阶段存储在本地 JSON 文件中，方便演示和调试。后续可以替换为 SQLite、MySQL 或云端数据库，数据结构已经比较清晰。

### 7.10 边缘 AI 怎么回答

建议说法：

> 当前系统已经在肌电模块中使用边缘 AI 模型。我们先在上臂端通过 ADC 采集肌电信号，提取 raw、baseline、drop、rectified、envelope、RMS 等特征；PC 端采集 relax、weak、active 三类数据训练随机森林模型；训练后导出为 STM32 可编译运行的 C 模型，在上臂端实时推理肌肉参与状态。为了提高康复场景下的稳定性，模型输出还会结合屈肘角度和动作阶段进行框定，使肌电判断符合当前动作过程。

如果评委问：

> 你这个 AI 模型在哪里？

可以回答：

> 肌电 AI 模型分为训练端和部署端。训练端在 `model_train/EMG` 中，包括数据采集脚本、数据集、随机森林训练脚本和训练报告；部署端是导出的 `emg_participation_model.c/.h`，已经集成进 STM32 上臂端工程。模型输入是基线归一化后的 6 个特征，输出是放松、轻微发力和正常发力三类状态。

如果评委继续问：

> 为什么模型输出还要根据角度框定？

可以回答：

> 因为康复训练不是单纯肌电分类。肌电信号容易受电极接触、皮肤阻抗和瞬时噪声影响，如果只看肌电，可能在没有完成有效动作时也出现强发力。我们把边缘 AI 输出和屈肘角度、动作阶段状态机结合，相当于给模型结果加上康复动作约束，使结果更符合实际训练逻辑。

不要说：

- “这是临床级 AI 诊断模型。”
- “所有人都能准确识别。”
- “肌电模型完全不受佩戴影响。”

## 8. 评委高频问题与回答

### 问题 1：这个作品和普通运动手环有什么区别？

回答：

> 普通手环主要关注步数、心率等通用健康指标，而我们的作品面向上肢康复训练，重点是关节角度、动作次数、动作完成度、训练评分和康复建议。它使用双 IMU 计算相对姿态，更适合康复动作评估。

### 问题 2：为什么选择上肢康复？

回答：

> 脑卒中和术后患者常需要长期上肢康复训练，但居家训练缺少专业指导，动作是否标准也难以量化。上肢动作比较适合通过可穿戴传感器采集，因此我们选择这个方向做软硬件一体化原型。

### 问题 3：动作识别准确吗？

回答：

> 当前原型可以稳定完成四类动作的实时识别和评估，但它还不是临床级系统。准确性会受佩戴位置、个体动作习惯和传感器漂移影响。我们后续计划通过标准动作数据集和更多受试者数据进行标定和模型训练。

### 问题 4：如果佩戴位置变了怎么办？

回答：

> 佩戴位置变化会影响角度估计，所以实际产品需要加入佩戴校准流程。当前原型通过相对姿态和动作阈值降低影响，后续可以加入开机校准、零点校准和个体化参数。

### 问题 5：系统能不能离线运行？

回答：

> 基础训练流程可以在设备端运行，Web 主要用于大屏展示和历史分析。时间同步和远程展示依赖网络，但动作采集和训练判断不完全依赖云端。

### 问题 6：为什么训练历史用 JSON，不直接用数据库？

回答：

> 当前是比赛原型，JSON 更轻量，便于调试和演示。数据结构已经包含动作、次数、角度、完成度和评分，后续替换为数据库并不影响系统架构。

### 问题 7：健康数据有什么用？

回答：

> 康复训练需要关注身体负荷。心率、血氧、HRV、疲劳等指标可以辅助判断训练强度是否合适，避免患者在状态不佳时过度训练。

### 问题 8：有没有安全性设计？

回答：

> 当前主要有训练状态显示、健康指标监测、动作完成度反馈和异常断连显示。后续可以加入心率过高提醒、训练中止提醒、跌倒检测和医生端报警。

### 问题 9：作品后续怎么改进？

回答：

> 后续主要有四个方向：第一，增加标准动作数据采集，提高动作识别准确率；第二，加入个体化校准；第三，把 JSON 存储升级为数据库或云端平台；第四，优化硬件形态，做成更轻便的一体化臂带。

### 问题 10：你们最大的技术难点是什么？

回答：

> 最大难点是把多传感器、嵌入式实时处理、无线通信、屏幕交互和 Web 可视化整合成一个稳定闭环。单独做角度显示不难，难的是让设备端训练、Web 端展示、历史记录和分析建议同时稳定工作。

### 问题 11：为什么肌电模型选择随机森林？

回答：

> 肌电特征维度不高，主要是基线归一化后的 raw、drop、rectified、envelope、RMS 等特征。随机森林对这类表格特征比较适合，训练速度快、可解释性强，而且可以导出为 C 代码在 STM32 上运行。相比大型神经网络，它更轻量，更适合当前 MCU 原型。

### 问题 12：为什么模型输出还要用角度框定？

回答：

> 肌电信号容易受到电极接触、皮肤阻抗、佩戴位置和瞬时噪声影响。康复训练评估不应该只看肌电，还要看动作是否进入有效屈肘区间。所以我们用屈肘角度和动作阶段对 AI 输出做框定，让结果符合“有动作幅度、有主动发力、有完整动作过程”的康复逻辑。

### 问题 13：你们的通信链路有什么技术点？

回答：

> 上臂端通过 ESP8266 接入 WiFi，训练数据和健康数据通过 MQTT 上传到 Web 后端。STM32 端没有简单依赖完整 MQTT 库，而是根据 MQTT 3.1.1 协议构造 CONNECT 和 PUBLISH 报文，再通过 TCP 发送。这样可以减少库依赖，也能更清楚地控制嵌入式端资源。

### 问题 14：为什么时间同步用 HTTP？

回答：

> 设备需要和 Web 端显示时间保持一致。我们让上臂端通过 HTTP 请求 Web 的时间接口，写入 RTC，之后由 RTC 本地走时。这样比频繁访问网络时间更可控，也能减少 WiFi 阻塞对训练实时性的影响。

### 问题 15：Web 端怎么实现实时刷新？

回答：

> 后端会统一接收 MQTT 或 HTTP 上传的数据，先解析成标准字段，再缓存最新状态。前端周期请求或接收实时事件后更新角度、评分、设备状态和健康数据。训练结束时，结果包会被写入本地历史记录，后续用于评分趋势和康复分析。

## 9. 演示时的注意事项

### 9.1 演示前检查

1. 上臂端和手腕端都已上电。
2. Web 服务已启动。
3. 电脑和设备在同一网络。
4. Web 首页能显示设备数据。
5. 上臂端时间显示正常。
6. 选择一个最稳定的动作作为主演示动作。
7. 历史记录页面提前确认有数据。
8. 健康监测界面提前确认能显示最新数据。

### 9.2 演示动作建议

优先顺序：

1. 前臂旋转：动作直观，适合展示双 IMU 相对姿态和前臂角度实时上传。
2. 肘关节屈伸：最适合展示角度、次数、完成度、边缘 AI 肌电模型和角度框定逻辑。
3. 手臂外展：作为补充动作，说明系统支持多动作训练。
4. 肩部上举：作为补充动作，说明系统支持肩部活动范围评估。

推荐现场主流程：

1. 先做前臂旋转，建立评委对“角度实时变化”的直观印象。
2. 再做肘关节屈伸，引出肌电边缘 AI 模型和角度框定。
3. 最后快速展示 Web 历史记录和 AI 康复分析。

- “这是医疗级诊断设备。”

多说：

- “这是康复训练评估原型。”

### 9.5 现场兜底演示顺序

如果现场时间、网络或肌电状态不稳定，按下面顺序降级：

1. 必讲：前臂旋转。只要 Web 端能看到角度变化，就能说明双 IMU 相对姿态链路打通。
2. 必讲：肘关节屈伸。重点展示屈肘角度、次数、完成度和评分。
3. 可讲：肌电边缘 AI。稳定就现场展示，不稳定就讲训练数据、模型部署和角度框定逻辑。
4. 可讲：健康监测。作为系统完整性补充，不要占用太多时间。
5. 必讲：历史记录和 AI 康复分析。用于收尾，强调作品不是一次性传感器演示。

兜底话术：

> 现场演示我优先展示最稳定、最能体现核心技术的两条链路：前臂旋转展示双 IMU 相对姿态，肘关节屈伸展示角度评估和肌电 AI 融合。其他健康监测和历史分析作为扩展功能展示。
