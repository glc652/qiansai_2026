## 一、项目解决的问题

### 1. 源码能够确认的产品能力

从四个工程的实际职责可以确认，系统围绕“上肢康复训练过程的动作感知、训练评价、健康状态采集、反馈交互和数据展示”组织：

- 上臂端采集上臂 LSM6DSR IMU 和 EMG，结合手腕端姿态/健康数据，计算肘屈伸、前臂旋转、肩部外展、肩部上举等动作的角度、动作状态、重复次数、完成度和训练评分。
- 手腕端采集自身 LSM6DSR IMU，并驱动 MKS142 健康监测模块，接收心率、血氧、微循环、疲劳、血压和 HRV 等结果，再通过串口发送给上臂端。
- 上臂端提供 LCD/触摸/语音/振动等现场人机交互，并通过 ESP8266 将训练和健康数据上传到 Web 侧。
- Web 端负责 HTTP/MQTT 接入、字段解析、状态归一化、历史 JSON 保存、训练统计和浏览器实时展示。
- APP 2.0 通过 HTTP 获取 Web 后端结果，提供家属端首页、实时、历史、健康、趋势和 AI 建议，并用 IndexedDB 保留已同步数据。

### 2. 目标康复场景

代码明确覆盖上肢动作训练和健康监测，但具体面向脑卒中、肩周炎、术后康复、老年人或哪一类患者，以及动作处方、适应症和临床目标，代码没有明确证明，均为【需要人工补充】。

可以在答辩中使用的谨慎表述是：本系统面向需要进行上肢功能训练和过程监测的使用者，通过双端穿戴式感知、动作评价、健康数据和家庭端展示形成辅助康复闭环。具体疾病适用范围和医学效果必须由产品资料、医生方案或实验数据补充。

### 3. 系统解决方案的边界

系统当前真正解决的是“如何采集并组织训练相关数据、如何在设备端实时评价动作、如何将结果传给家属/网页端并形成历史趋势”。它不是代码意义上的自动康复执行器：上臂端源码中未发现闭环电机/执行器控制，Web 的 `/api/start`、`/api/stop` 只修改 Web 状态，是否向设备下发训练控制【需要人工确认】。

## 二、系统架构

### 1. 总体结构

```text
患者/使用者
   │佩戴、动作、触摸、按键、语音交互
   ▼
手腕端 STM32U575
   │LSM6DSR 姿态；MKS142 健康模块；本地 LCD/触摸/振动
   │USART1 二进制姿态/健康帧 ↔ 上臂端
   ▼
上臂端 STM32U575
   │上臂 IMU + EMG；多源融合；动作分类；计次/评分；LCD/触摸/语音
   │USART2 ↔ ESP8266；MQTT/HTTP → Web
   ▼
Web Flask/MQTT 服务
   │解析、归一化、历史、训练分析、SSE/REST、AI 服务适配
   ├──────────────► 浏览器 Web 仪表盘
   └──────────────► 手机 APP 2.0（Node 代理或直接 API）
```

### 2. 患者/使用者与各端关系

- 使用者是数据产生者和交互者：动作改变 IMU/EMG/健康读数，触摸/按键/语音改变设备页面或模式。
- 手腕端是穿戴式传感与交互节点：姿态和健康数据在此产生/接收，向上臂端发送；手腕端也接收上臂端 ACK、训练/健康/回主页事件。
- 上臂端是当前系统的主要动作评价节点：接收手腕帧，融合本地 IMU/EMG，计算动作和评分，再控制本地 UI 与上传。
- Web 是网络接入和服务层：接收上臂端上传，不直接访问传感器。
- APP 是移动消费端：主动读取 Web API，不直接访问 MCU 传感器。

### 3. 控制关系的确定与不确定部分

源码能确认手腕端接收上臂端的 4 字节事件/ACK，并据此更新训练、回主页、健康模式请求；上臂端能确认解析手腕端发送的状态帧。Web/APP 能确认修改 Web 自身训练状态和显示页面，但 Web/APP 到 MCU 的控制闭环没有在对应工程中完整出现，设备实际控制方向【需要人工确认】。

## 三、完整数据链

### 1. 运动数据链

```text
上臂 LSM6DSR + 手腕 LSM6DSR
 → SPI 读取原始加速度/角速度
 → 零偏校准、死区、低通、六轴姿态融合
 → 上臂/手腕相对姿态与角度
 → Rehab_ClassifyRule 动作分类
 → 四类 Eval_Update 状态机计次
 → completion/amplitude/angle/speed/score
 → UI 快照与 MQTT/HTTP key-value payload
 → Web normalize_realtime
 → SSE/REST 或 APP 2 秒轮询
 → 实时页面、训练历史、趋势分析
```

上臂端 `StartSensorTask` 约 5 ms 运行一次；IMU 配置为 208 Hz。`StartAlgoTask` 约 100 ms 执行融合和动作评价。手腕端姿态任务也以 5 ms 周期运行，并每 50 ms 发送普通姿态帧。

### 2. EMG/生理数据链

#### EMG

```text
上臂 ADC4 + TIM3 TRGO + GPDMA circular
 → 半满/全满回调释放信号量
 → EmgTask / EmgSensor_ProcessSample
 → baseline、整流、低通、RMS、百分位和迟滞
 → active/strength/mode
 → AlgoTask 参与肘屈伸评分
 → UI 与上传字段
```

源码还显示 `EMG_SENSOR_MODEL_ENABLE=0`，当前默认是范围/规则型处理，不是包含的 EMG 模型文件。手腕端也有 EMG 驱动文件，但 `MX_FREERTOS_Init` 未创建有效 EmgTask，`StartEmgTask` 只是延时循环，因此手腕端 EMG 当前运行链【需要人工确认/以最终构建宏为准】。

#### 生理/健康数据

```text
MKS142 健康模块
 → USART2 38400-8N1 字节中断
 → MKS142_FeedByte 状态机
 → MKS142_ParseFrame 解析 88 字节帧
 → g_heart_data / g_heart_valid / frame tick
 → HeartRateTask 清除超时数据或通知健康有效
 → WirelessLink_BuildHealthFrame
 → USART1 → 上臂端 → MQTT/HTTP
 → Web normalize_health → JSON 历史
 → Web/APP 心率、血氧、血压、HRV 等展示
```

MKS142 的指标在当前手腕端代码中表现为模块输出；APP/Web 没有实现 PPG、心率或血氧原始算法。具体 MKS142 内部算法【需要人工确认】。

### 3. 训练结果链

动作评价状态机在上臂端累积峰值、幅度、进入/退出阈值和次数；`rehab_eval.c` 的四类评估函数生成训练快照。上臂端 payload 使用 `pg,a,n,g,s,m,av,em,e,ab,sh` 等字段表达页面、动作、次数、评分、最大/平均角度、肌电和多关节角度。

Web 端在接收结果页或训练事件时写入训练历史；`build_analysis_payload` 再按最近 7 天或最近 10 条记录计算平均评分、完成度、幅度、活跃天数、恢复指数和薄弱动作。APP 端读取 `/api/history` 和 `/api/analysis`，并在 IndexedDB 中合并缓存。

### 4. 设备控制数据链

源码明确的设备控制/事件方向：

```text
手腕端 UI/状态
 → 上臂端接收 4 字节 ACK/事件
 → 更新训练/主页/健康请求标志
 → 上臂端 UI/上传状态改变
```

明确事件值包括 `A5 5A C3 3C` 普通 ACK、`A5 5A D4 4D` 训练开始、`A5 5A E5 5E` 回主页、`A5 5A F6 6F` 健康模式。上臂端向手腕端发送这些事件的完整发送时机，以及 Web/APP 是否能触发真实设备事件【需要人工确认】。

### 5. 网络数据链

```text
上臂端 UART2 → ESP8266 AT 指令
 → Wi-Fi 连接 → MQTT 3.1.1 QoS0 或 HTTP 校时
 → MQTT rehab/upper/realtime / rehab/upper/health
 → Web paho MQTT 或 HTTP /upload
 → latest_data/latest_health
 → REST/SSE → 浏览器；APP 通过 Node /proxy 或 API_BASE 读取
```

上臂端源码记录的目标地址是 `10.35.253.211:1883` 和 `10.35.253.211:5000/api/device-time`；Web 默认配置是本机 `127.0.0.1:1883`、`rehab/upper/#`，实际部署是否一致【需要人工确认】。

## 四、四端分工

### 1. 手腕端：传感与交互节点

职责：LSM6DSR 姿态采集；MKS142 健康模块控制/解析；本地屏幕、触摸、按键、振动；通过 USART1 发送姿态和健康帧，接收上臂端事件。它将健康和腕部姿态靠近传感器处理，减少上臂端直接连接健康模块的负担。

边界：当前源码中 `StartAlgoTask` 为空任务，手腕端不应被描述为完成了主要康复动作评分。

### 2. 上臂端：主要感知融合和训练评价节点

职责：上臂 IMU、EMG；接收手腕帧；六轴姿态处理；动作规则分类；计次和评分；本地交互；ESP8266 上网。它是“实时动作结果”的主要产生端。

### 3. Web：数据接入和服务层

职责：HTTP/MQTT 接入、解析、归一化、历史持久化、统计分析、SSE 推送和外部 AI 适配。它不处理 MCU 原始波形。

### 4. APP：家属端移动交互层

职责：读取 Web JSON，展示实时/历史/健康/趋势/AI 建议；IndexedDB 离线保留；Node 代理或 API 地址配置；APK 以 WebView 复用网页资源。它不直接操作传感器。

## 五、通信架构

### 1. 手腕端 ↔ 上臂端 USART1

接口：源码配置 9600-8N1；注释提到 HC-05，但具体无线模块型号【需要确认】。

#### 手腕 → 上臂普通姿态帧

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 1 | `0xAA` |
| 1~2 | 2 | seq，小端 |
| 3~6 | 4 | tick，小端 |
| 7~12 | 6 | acc_mg[3]，int16 |
| 13~18 | 6 | gyro_dps_x10[3] |
| 19~24 | 6 | angle_x100[3] |
| 25~26 | 2 | heart_rate |
| 27 | 1 | status：IMU/心率有效位 |
| 28 | 1 | battery_percent |
| 29 | 1 | status2：ACK、sleep、battery valid、health 状态等 |
| 30 | 1 | 8 位累加校验 |

总长度 31 字节；手腕端每 50 ms 发送。上臂端 `WirelessLink_PushByte`/`DecodeFrame` 进行同步、长度和累加和校验，异常帧统计并重新同步；手腕端以 30 s 超时判定连接/数据失效。

#### 手腕 → 上臂健康帧

帧头 `0xAB`，总长 17 字节：seq 2、tick 4、heart_rate、spo2、micro_circ、fatigue、sbp、dbp、sdnn、rmssd、status、checksum。健康模式下约 200 ms 发送，但前提是健康页面 active 且数据有效。

#### 上臂 → 手腕控制/事件

已确认手腕端解析 `A5 5A` 起始的 4 字节码；具体上臂端发送函数/时序【需要人工确认】。

### 2. MKS142 → 手腕端 USART2

接口 38400-8N1；`0x8A` 开启采集、`0x88` 停止、`0x98` 睡眠、`0x00` 唤醒。数据帧 88 字节、帧头 `0xFF`，`MKS142_FeedByte` 等待帧头后收满固定长度，解析 PPG/心率/血氧/微循环/疲劳/血压/SDNN/RMSSD。源码所述协议约束是帧内不再出现 `0xFF`，具体厂商协议和校验字段【需要人工确认】。

### 3. 上臂端 → ESP8266 → MQTT/HTTP

USART2 115200-8N1，ESP8266 使用 AT 指令；上臂端自行构造 MQTT 3.1.1 CONNECT/PUBLISH，QoS 0。主题：`rehab/upper/realtime`、`rehab/upper/health`。实时上传约 500 ms，健康数据约 10 s 并按 seq 去重；HTTP `GET /api/device-time` 用于校时。payload 是逗号分隔的 key-value 文本，不是 JSON。

源码可确认的字段示例：

- 页面/状态：`t,pg,ue,ub,wb,uba,wba`
- 训练：`pg,a,n,ang,e,ab,sh`
- 结果：`t,pg,a,n,g,s,m,av,em,e,ab,sh`

但 Web 的 `parse_kv_payload` 只接受带 `=` 的键值字符串；上臂端文档中字段列表未完全展示赋值符号和最终发送样例，真实字节级 payload【需要人工确认】。

### 4. 设备/网关 → Web

HTTP `POST /upload` 可接 JSON、表单或原始文本；MQTT Web 默认订阅 `rehab/upper/#`、QoS 0。Web 侧无 CRC、固定长度、认证或签名校验。MQTT 异常断开自动重连，延迟 1~30 秒。

### 5. Web → APP/浏览器

Web 提供 `/api/latest`、`/api/history`、`/api/health_history`、`/api/analysis`；浏览器还可使用 `/events` SSE，前端失败时轮询。APP 2.0 每 2 秒主动请求 `/api/latest`，每 15 秒同步历史/健康/分析；Node `server.js` 提供 `/proxy/api/*` 反向代理，默认监听 5175。

## 六、核心技术排名

### 第一位：上臂端多源姿态与康复动作评价

证据：`upper-arm/Core/Src/imu_processing.c:IMUProc_AttitudeUpdate6Axis`、`app_freertos.c:Rehab_ClassifyRule/StartAlgoTask`、`rehab_eval.c`。

价值：把上臂 IMU、手腕 IMU、动作阈值、角速度、幅度和训练状态组合为可解释的动作/次数/评分结果，是作品从“传感器读数”变成“康复评价”的核心。

### 第二位：EMG 实时处理与评分融合

证据：`emg_sensor.c:EmgSensor_ProcessSample/ProcessHalfBuffer/ProcessFullBuffer`；`rehab_eval.c` 中肘屈伸评分权重包含 EMG。

价值：具备 baseline、整流、低通、RMS、百分位、active/strength 和迟滞；但必须明确 `EMG_SENSOR_MODEL_ENABLE=0`，当前运行的是范围规则，不是 RF/模型算法。

### 第三位：双端二进制协议和健康数据链

证据：手腕 `wireless_link.c:WirelessLink_BuildWristFrame/BuildHealthFrame`；上臂 `wireless_link.c:WirelessLink_PushByte/DecodeFrame/DecodeHealthFrame`；手腕 `mks142.c:MKS142_FeedByte/ParseFrame`。

价值：固定长度、帧头、状态位、序号、校验和、超时和中断字节流解析让双端能稳定交换多源数据。

### 第四位：实时调度和异步数据通道

证据：两端 `MX_FREERTOS_Init`、`StartSensorTask`、`StartAlgoTask`、`StartWirelessTask`、`StartEspUploadTask`、`StartDisplayTask`；EMG DMA 回调和信号量。

价值：采集、算法、通信、UI 解耦。答辩应说明实际运行路径和预留但未启用的任务，不能把未创建的任务包装成已运行功能。

### 第五位：Web/APP 数据闭环与离线展示

证据：Web `ingest_device_payload/normalize_*/build_analysis_payload`；APP `mergeRecords/loadLocalData/startBackgroundSync`。

价值：设备输出被统一为实时、历史、分析数据；APP 断网仍可看已缓存记录。但它属于系统工程集成亮点，不应说成传感器创新算法。

## 八、完整工作流程

1. 使用者佩戴上臂端和手腕端，设备上电；两块 STM32U575 完成 HAL、时钟、GPIO、DMA、ADC、SPI、TIM、I2C、UART 和 FreeRTOS 初始化。
2. 手腕端启动 LSM6DSR 和 MKS142；上臂端启动上臂 LSM6DSR、EMG、显示和 ESP8266 链路。IMU 进行 WHO_AM_I、复位、寄存器配置和静止零偏校准。
3. 手腕端 5 ms 读取姿态，USART2 中断接收 MKS142 88 字节健康帧；上臂端 5 ms 读取 IMU，EMG 由 TIM3/ADC/GPDMA 提供数据。
4. 两端各自做姿态预处理；手腕端每 50 ms 打包普通姿态帧、健康模式下约 200 ms 打包健康帧发给上臂端。
5. 上臂端解析手腕帧，将相对姿态、上臂姿态、EMG 和心率/健康状态放进算法快照；约 100 ms 执行动作规则和训练评价。
6. 当角度/速度满足进入阈值并在退出阈值完成动作时，评估状态机增加次数，计算幅度、完成度和评分；UI 显示实时反馈，并可振动/语音提示。
7. 上臂端每约 500 ms 构造训练状态或结果上传，健康数据按实现约 10 s 上传；ESP8266 通过 AT 指令接入 Wi-Fi，再经 MQTT QoS0 发送到 Web。实际 MQTT 建连成功与部署地址【需要人工确认】。
8. Web 接收并解析 payload，按 page/health 字段区分实时与健康数据，归一化后写入最新状态和历史文件；SSE 或 REST 向浏览器提供结果。
9. Web 仪表盘实时显示角度、动作、次数、评分、肌电、设备状态、心率/血氧；APP 每 2 秒轮询最新数据，每 15 秒合并历史和分析数据，并可离线浏览已有记录。
10. 训练结束后 Web 保存结果；后端统计最近记录并计算恢复指数、薄弱动作和建议；APP/网页展示趋势，AI 接口可基于这些上下文生成辅助说明。

## 九、答辩技术亮点

### 亮点 1：双 IMU 相对姿态支撑上肢动作评价

- 解决的问题：单个 IMU 难以直接描述上下臂相对运动。
- 方法：上臂端和手腕端分别做六轴姿态融合，再在上臂算法任务中组合相对 pitch/roll/yaw。
- 实现：`imu_processing.c:IMUProc_AttitudeUpdate6Axis`、`app_freertos.c:StartAlgoTask`。
- 效果：输出肘屈伸、前臂旋转、肩外展、肩上举等动作相关角度。
- 注意：无磁力计时 yaw 会漂移，绝对精度和临床有效性【需要人工确认】。

### 亮点 2：多源数据参与训练评价

- 解决的问题：只看角度无法反映动作完成质量和主动肌肉参与。
- 方法：角度/速度/幅度/次数与 EMG active/strength 融合；肘屈伸评分包含 EMG 权重，其余动作按完成度和幅度评分。
- 实现：`rehab_eval.c` 各 `*Eval_Update/Update*Scores`、`emg_sensor.c`。
- 效果：形成动作次数、幅度、完成度和评分，而不是单一角度显示。
- 限制：EMG 模型宏关闭，当前运行的不是 RF 模型；权重医学依据【需要人工确认】。

### 亮点 3：固定帧协议保证双端可解析

- 解决的问题：UART 字节流存在丢字节、错位和混合状态帧风险。
- 方法：帧头、固定长度、序号、tick、状态位和 8 位累加校验；接收端字节状态机重新同步。
- 实现：`wireless_link.c`、`MKS142_FeedByte`、`HAL_UART_RxCpltCallback`。
- 效果：健康和姿态字段能在两个 MCU 间明确传输，并可通过超时清除失效数据。
- 限制：8 位累加和抗碰撞能力有限；是否升级 CRC/重传【需要人工确认】。

### 亮点 4：实时任务与 DMA 解耦采集/算法/UI

- 解决的问题：EMG 高速采样、姿态更新、通信和显示同时运行时互相阻塞。
- 方法：FreeRTOS 任务分工；EMG 定时触发 ADC，GPDMA circular 半满/全满通知处理任务；UI 通过 DMA 刷屏。
- 实现：`MX_FREERTOS_Init`、`StartSensorTask`、`StartEmgTask`、ADC DMA 回调、`StartDisplayTask`。
- 效果：理论上采集和显示互不占用同一长阻塞路径。
- 诚实边界：上臂 SensorTask 当前调用阻塞式 `LSM6DSR_ReadRaw`，并非已验证的 IMU DMA 路径；手腕 EMG 任务未实际创建。

### 亮点 5：设备—Web—APP 数据闭环

- 解决的问题：设备现场反馈和家庭端长期观察割裂。
- 方法：上臂 MQTT/HTTP 上传，Web 统一解析并保存历史，APP API 拉取并 IndexedDB 增量合并。
- 实现：上臂 `StartEspUploadTask`；Web `ingest_device_payload`；APP `mergeRecords/startBackgroundSync`。
- 效果：实时训练、健康历史、趋势和家属端展示统一使用同一套数据。
- 限制：MQTT QoS0、匿名/明文配置和无用户鉴权不适合直接宣称生产级可靠性。

### 亮点 6：面向掉线和过期数据的降级处理

- 解决的问题：无线链路或后端暂时不可用时避免继续显示旧数据。
- 方法：MCU 侧无线/健康超时；Web 侧 MQTT 自动重连、SSE/轮询回退；APP 侧 IndexedDB 离线查看。
- 实现：上臂/手腕超时变量和状态位；Web `start_mqtt_subscriber`、`realtime_events`；APP `pollRealtime/loadLocalData`。
- 效果：显示层可区分新鲜、等待和离线状态。
- 边界：没有确认离线设备数据缓存和补发队列，离线回传【需要人工确认】。

## 十、评委可能追问的问题

### 硬件类

1. 主控型号是什么？
   - 答：上臂端和手腕端工程均指向 STM32U575RIT6/STM32U575RITx，系统时钟配置为 160 MHz；具体 PCB 版本【需要确认】。
2. 上臂端采集哪些传感器？
   - 答：LSM6DSR IMU、EMG ADC，以及电池 ADC；具体 EMG 电极型号【需要确认】。
3. 手腕端采集哪些传感器？
   - 答：LSM6DSR IMU 和 MKS142 健康模块；MKS142 内部传感器型号【需要确认】。
4. 为什么要两块 IMU？
   - 答：源码在上臂端使用上下肢相对姿态来计算动作角度；单块 IMU 无法直接得到两段肢体相对运动。
5. 为什么没有磁力计？
   - 答：源码是六轴融合，yaw 主要依靠陀螺积分，长期漂移是已知限制；是否满足目标动作精度需要实测。
6. 传感器采样率是多少？
   - 答：IMU 配置 208 Hz，任务约 5 ms；EMG 由 TIM3/ADC/GPDMA 触发，具体有效采样率以最终时钟和 ADC 配置核验。

### 嵌入式软件类

7. 是否使用 RTOS？
   - 答：两块 STM32 工程使用 CMSIS-RTOS2 API 和 FreeRTOS 内核；任务包括 Sensor、Algo、Wireless、Display、健康/EMG/上传等，但部分任务是预留或未创建。
8. 任务如何避免互相覆盖数据？
   - 答：工程使用全局快照、临界区、信号量和队列；具体每个快照字段的完整并发保护范围应现场引用源码核对。
9. main 做什么？
   - 答：HAL、时钟、GPIO、缓存、DMA、ADC、SPI、TIM、I2C、UART 初始化，随后初始化 RTOS 对象和任务并启动调度器；main 的 while 不承担主要业务。
10. 为什么 IMU 配置 208 Hz、任务 5 ms？
   - 答：208 Hz 与 5 ms 约 200 Hz 不完全相同，可能存在采样丢弃/重复读取或配置与任务不匹配；最终实现应通过运行日志或逻辑分析仪确认。
11. SPI DMA 是否真的用于 IMU？
   - 答：SPI1 DMA 回调和信号量存在，但当前 SensorTask 明确调用阻塞式 `LSM6DSR_ReadRaw`，不能宣称 IMU 已使用 DMA；LCD SPI3 DMA 证据更明确。
12. 手腕端为什么有 AlgoTask 却没有本地动作算法？
   - 答：`StartAlgoTask` 当前为空循环，主要动作分类/评分位于上臂端；这体现了职责分工，也应坦诚说明未启用功能。

### 算法类

13. 姿态融合是什么原理？
   - 答：陀螺积分提供短期动态，加速度重力方向修正滚转/俯仰；代码使用误差反馈、四元数积分和归一化，参数可见 `IMUProc_AttitudeUpdate6Axis`。
14. yaw 漂移如何解决？
   - 答：六轴系统没有磁航向绝对参考，源码不能证明完全解决；动作算法应减少对绝对 yaw 的依赖，具体补偿策略【需要确认】。
15. 动作如何分类？
   - 答：`Rehab_ClassifyRule` 使用角度、角速度、上臂稳定性以及 enter/exit 阈值，并有约 1500 ms 动作锁存抗抖。
16. 如何计数避免一次动作多次计数？
   - 答：`rehab_eval.c` 使用进入阈值、峰值记录、退出阈值和峰值/幅度条件形成状态机；完整阈值应引用相应 `*Eval_Update`。
17. 评分如何计算？
   - 答：源码分析显示肘屈伸为完成度 40%+幅度 40%+EMG 20%，其他三类为完成度 50%+幅度 50%；权重实验依据【需要确认】。
18. EMG 处理步骤是什么？
   - 答：warm-up/baseline、去基线整流、低通、窗口 RMS、百分位范围、历史稳定值和 active/strength 迟滞；当前模型宏为 0，不能称为机器学习模型。
19. MKS142 的心率/血氧算法在哪里？
   - 答：手腕端只解析 MKS142 输出的 88 字节健康帧，源码未实现 PPG 到心率/血氧的完整算法；内部算法【需要确认】。
20. Web 的恢复指数是医学指标吗？
   - 答：不是源码能证明的医学指标；Web 是按训练评分、完成度、幅度和活跃天数加权的启发式统计，医学验证【需要确认】。

### 通信类

21. 手腕到上臂的姿态帧格式是什么？
   - 答：0xAA、31 字节、seq/tick、加速度、角速度、角度、心率、状态、电量和 8 位累加和。
22. 健康帧格式是什么？
   - 答：0xAB、17 字节、seq/tick、心率、血氧、微循环、疲劳、血压、SDNN、RMSSD、状态和校验。
23. 为什么用累加和而不是 CRC？
   - 答：当前代码确实用 8 位累加和；它实现简单但检错能力有限，采用原因和升级方案【需要确认】。
24. MKS142 如何同步？
   - 答：USART2 字节中断送入 `MKS142_FeedByte`，以 0xFF 作为帧头、固定 88 字节收满后解析，并对异常帧重新同步。
25. MQTT 使用什么 QoS？
   - 答：上臂端自建 MQTT 3.1.1 PUBLISH，源码记录 QoS0；Web paho 订阅也为 QoS0。丢包补发和服务质量实测【需要确认】。
26. MQTT 和 HTTP 各做什么？
   - 答：MQTT 承载实时/健康发布；HTTP `/api/device-time` 用于校时，上臂端也存在 HTTP 上传路径的配置/实现线索；最终启用路径【需要确认】。
27. 无线断开怎么处理？
   - 答：上臂/手腕有连接超时和状态失效；ESP MQTT 客户端/Web paho 有重连逻辑；是否有设备侧应用层重传【需要确认】。

### 系统架构类

28. 为什么动作算法放上臂端而不是 Web？
   - 答：上臂端需要低延迟本地反馈，且直接拥有上臂 IMU/EMG 和手腕帧；Web 只收到结果字段，没有原始波形链。
29. 为什么健康模块放手腕端？
   - 答：代码上 MKS142 接在手腕端 USART2，本地健康 UI 和手腕佩戴点更接近健康采集；产品医学/佩戴依据【需要确认】。
30. APP 和 Web 为什么都存在？
   - 答：Web 负责服务、接入、历史和多终端 API；APP 是面向家属的移动交互和离线缓存，两者职责不同。
31. APP 是原生还是网页？
   - 答：业务是 HTML/CSS/JS；APK 是原生 Activity 承载 WebView，资源与 `app2.0` 一致。
32. 断网时 APP 能做什么？
   - 答：可以用 IndexedDB 显示已经缓存的历史、健康、分析和最近快照；不能从源码证明可继续接收设备实时数据或离线上传。
33. Web 和 APP 是否直接连接 MCU？
   - 答：没有直接 MCU 驱动；上臂端通过 ESP8266 上网，Web 接入后 APP 查询 Web。

### APP/Web 类

34. APP 刷新周期是多少？
   - 答：实时 `/api/latest` 每 2000 ms；历史、健康、分析每 15000 ms；回到前台立即刷新。
35. Web 浏览器如何实时刷新？
   - 答：优先 SSE `/events` 条件变量推送，EventSource 不可用或断开时使用约 400 ms 轮询。
36. APP 如何避免历史重复？
   - 答：`recordKey` 优先用 id，健康记录可用 seq+时间，其他记录用时间/动作；`mergeRecords` 用 Map 合并。
37. AI 是否在本地运行？
   - 答：不在 APP 本地；APP 请求 `/api/ai_chat`，Web 后端调用外部模型接口。
38. Web 是否直接存数据库？
   - 答：当前源码使用训练和健康 JSON 文件，临时文件写入后 `os.replace`；数据库事务和并发一致性【需要确认】。

42. 数据过期如何处理？

## 十二、答辩使用建议

推荐答辩主线：

> 佩戴式双端首先在设备侧完成实时感知和动作评价：手腕端采集姿态与健康数据，上臂端融合双 IMU 和 EMG，使用规则状态机完成动作识别、计次和评分；随后上臂端通过 ESP8266 将结果发送到 Web，Web 负责统一接入、历史分析和多端服务，APP 面向家属提供实时观察、趋势和离线查看。系统的核心不在普通 UI，而在双端数据融合、可解释动作评价、固定帧通信和从设备到家属端的数据闭环。

答辩时必须主动说明三点：

1. 手腕端当前主要是传感/交互/转发节点，主要动作评分在上臂端。
2. EMG 模型文件被工程包含但默认未启用，当前是规则特征链。
3. Web/APP 的恢复指数、健康阈值和 AI 建议是应用层辅助分析，不能替代医学诊断；临床效果和实际部署指标需要实验材料补充。
